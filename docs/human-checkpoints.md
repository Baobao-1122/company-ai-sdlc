# 人工确认暂停点（Human Checkpoints）

> **文档 ID：** `CHECKPOINTS-v1`  
> **策略：** 稳健优先（低风险）  
> **受众：** Cursor Agent + 研发人员  
> **最后更新：** 2026-10-24

---

## 1. 总则

**默认模式：AI 主动引导 + 人工在 CP 介入。** Agent 负责宣布阶段、提问、给出回复选项；人只需在 `⏸` 处按选项回复。

**半自动执行：** Agent 可在**已确认范围内**连续读文档、写代码、跑测试；在 **CP 暂停点必须停止**，输出 **决策包**（判据 + 自检 + 推荐 + 编号选项）。

**禁止：** Agent 自行跳过 CP、开放式甩锅（「你觉得呢？」）、自行 commit/push/合并。

**主动引导细则：** [agent-active-guidance.md](agent-active-guidance.md)  
**判断要点（Allow/Stop）：** [decision-rubrics.md](decision-rubrics.md)

## 2. 暂停点一览

| ID | 名称 | 触发时机 | Agent 必须做什么 | 等人说什么 |
|----|------|----------|------------------|------------|
| **CP-01** | 需求对齐后 | 输出需求对齐表后；对齐表后附**设计草稿清单**，没有草稿写「无」（见 §2.1） | **停止**；不写代码、不拆设计 | 「确认」「OK」「按这个做」 |
| **架构审查** | 技术方案审查 | CP-02 之前，且命中 Skill `sdlc-architecture`：首版运行形态、运行方式变更、第一版跨系统契约、已有消费方的对外契约升主版本，或用户明确要求评审技术方案。小改动和按已接受架构实现**不触发**。子 Agent 结论为「这次不该审」时不在这里暂停 | 结论为「通过」或「要改」时**停止**。子 Agent 若改了文件，还原改动并使该轮作废。结论为「这次不该审」时把 `status` 写成 `not_required`，写未触发理由并进入 CP-02，不暂停 | 「通过」：「确认通过」/「暂停」。「要改」：「按审查改方案」/「维持方案：…」/「暂停」。「这次不该审」：不问 |
| **CP-02** | 设计拆分后 | 输出改动范围/验收/ commit 计划；涉及 schema 时含 migration 计划；命中业务数据影响面时含**只读**抽样对账计划；改 API/auth/金额/导出/敏感读时含**安全与输入校验**计划。若触发架构审查，须用户已回复「确认通过」、已「维持方案」，或子 Agent 判定这次不该审并已写下未触发理由。子 Agent 写出「通过」但人尚未回复「确认通过」时，不得输出 CP-02 | **停止**；不写代码 | 「开始实现」「可以动手」 |
| **CP-03** | 外部依赖阻塞 | 缺接口/数据/环境；或 **拟新增 CP-02 未声明的 npm 依赖** | **停止**；说明影响与选项 | 「mock 继续」「确认安装」「换方案」「暂停」等 |
| **CP-04** | 范围外问题 | 发现未提及的 bug、需改声明外文件 | **停止**；报告问题，不顺手修 | 「一起修」「只修 xxx」「跳过」 |
| **CP-05** | 实现+验证后 | 编码完成且验证命令已有明确结果；涉及 schema 时数据库变更链已执行或已确认环境阻塞；命中数据影响面时已完成只读对账并给出结论与问题；改 API/安全面时已完成**安全冒烟**且**无擅自写生产库** | **停止**；汇报结果，任一步失败时推荐 **Stop** | 「提交」「继续改 xxx」「下一项」 |
| **CP-06** | **每次 commit 前** | ① Code Review ② commit 计划 | **两步都停**；见 [code-review.md](code-review.md) | 步骤1：「确认提交/先修/忽略」步骤2：「确认提交」 |
| **CP-07** | 推送前 | 任何 `git push` 前 | 汇报分支与远端 | 「推送」 |
| **CP-08** | 合并 dev / PR | merge、PR merge、push dev 前 | Read `sdlc-pr-review`：Bugbot 整分支 diff，输出 [PR 审查结论](pr-review.md)；命中项目声明的可验算业务结果时写出人工判断块并停下 | 未命中：「去 GitHub Merge」/「先修 PR」。命中：先「口径接受」或「口径不接受：…」 |
| **CP-09** | 下一需求项 | 当前任务在 CP-05 已完成 | **停止**；用户指定下一项后，先把当前 `.sdlc/task-state.yaml` 移到 `.sdlc/history/`，在 `.sdlc/history/index.md` 追加一行，新任务状态的 `previousTask` 指向归档文件，再从 CP-01 开始（见 [task-state.md](task-state.md) §4.2、§4.5） | 「做下一项 FU-xxx」 |
| **CP-10** | 高风险操作 | deploy、SSH、**生产库写操作**、DMS 变更、删库 | **停止** | 负责人明确授权 |

### 2.1 CP-01 之前的设计草稿

需求常在讨论中逐步定下。CP-01 之前，Agent 可以按讨论结论改**文档**（产品说明、契约、技术方案），这些改动都是**设计草稿**：

- 只改文档。不改代码，不改 migration，不动任何数据库，不提交
- 进入 CP-01 时，对齐表后附**设计草稿清单**：每个改过的文件、改了什么。没有草稿时写「无」
- 用户「确认」后，清单里的草稿成为设计输入，写入 task-state 的 `drafts`。「修改：…」按意见改草稿，再列一次清单。「暂停」时草稿保留，但不作为设计依据
- 没列进清单的改动，不得作为设计依据。CP-02 前发现漏列，回到 CP-01 补列

## 3. 可自动执行（无需暂停）

以下条件**同时满足**时，Agent **不必**在步骤间等人：

| 动作 | 条件 |
|------|------|
| 读 AGENTS.md / docs | 任何时候 |
| 在同一任务内改**已声明**的文件 | CP-02 已通过 |
| migration prepare（生成或手写并检查）、应用至目标验收库、结构检查与依赖 API 冒烟 | CP-02 已通过且本次修改 schema；按设计顺序执行；**本步不含 harness** |
| **只读**业务数据抽样对账（查询/导出/对比），并整理结论与问题清单 | CP-02 已通过且计划已声明数据影响面；若同时改 schema，须在结构链成功**之后**、harness **之前**执行；**禁止**在对账中 INSERT/UPDATE/DELETE |
| 跑 `test:harness:ci` 等项目验证命令 | 结构链（如适用）已通过；业务数据只读对账（如适用）已执行并产出结论与问题清单（「有差异」仍可跑 harness；**未执行/缺证据/核对写库**则禁止）；在 CP-05 汇报前执行 |
| 同步更新与本次改动相关的 docs | CP-02 已通过 |
| 修复实现引入的 lint/类型错误 | 不扩大文件范围 |

**红线：** **生产环境数据库** — 无 **CP-10** 负责人授权，**禁止**任何写操作（含 DMS/脚本/Agent 代执行）。数据校验 = 核对；校验后只允许**结论与问题**；修数另开任务；不得以 reconcile / 对账 / 校验名义改删业务数据（**含非生产的业务表**，对账步骤仍只读）。详见 Rule **`data-redlines.mdc`**。

## 4. 标准流程与 CP 位置

```
[用户提任务]
     │
     ▼
┌─ 需求对齐 ─────────────────────────► CP-01 停 ◄── 等人确认
│
     ▼
┌─ 架构审查（条件触发）──────────────► 命中且结论为「通过」或「要改」时停
│                                      未命中、「这次不该审」、「维持方案」或已「确认通过」后继续
     ▼
┌─ 设计拆分 ─────────────────────────► CP-02 停 ◄── 等人「开始实现」
│
     ▼
┌─ 编码实现 ───┬─ 遇外部依赖 ────────► CP-03 停
│              └─ 遇范围外问题 ──────► CP-04 停
│
     ▼
┌─ 验证门禁（结构链 → 只读对账 → harness，如适用）► CP-05 停 ◄── 等人决定提交/下一项
│
     ├─ 用户说「提交」───────────────► CP-06 步骤1 Code Review（Bugbot）
     │                                      ↓
     │                               CP-06 步骤2 commit 确认
     ├─ 用户说「推送」───────────────► CP-07 停
     ├─ 用户说「提 PR / 合并 dev」──► sdlc-pr-review → CP-08 步骤1 停 → 人 Merge
     └─ 用户说「下一项」─────────────► CP-09 → 回到需求对齐
```

## 5. Agent 暂停话术（必须使用）

每个 CP 结束时，Agent 回复**必须**包含完整 **决策包**（见 [decision-rubrics.md](decision-rubrics.md) §2）：

`①目的` · `②判断要点` · `③Agent自检` · `④Agent推荐` · `⑤请你回复` · `⏸ CP-xx`

| CP | 结尾必须包含 |
|----|-------------|
| CP-01～10 | 决策包五块 + `⏸ CP-xx`；**禁止**仅有编号选项 |

## 6. 用户指令速查

| 你说 | Agent 行为 |
|------|-----------|
| 「对齐需求 xxx」 | 需求对齐 → **CP-01 停** |
| 「确认 / OK」 | 若停在 CP-01 → 可进入设计；若停在 CP-06 → 执行 commit |
| 「开始实现」 | 通过 CP-02 → 编码（范围内可自动跑验证） |
| 「跑 harness 验收」 | 验证阶段 → 完成后 **CP-05 停** |
| 「提交」 | 进入 **sdlc-review** → CP-06 步骤1 Review → 步骤2 commit |
| 「推送」 | **CP-07** → push |
| 「提 PR / 合并 dev」 | **sdlc-pr-review** → **CP-08 步骤 1**。命中可验算业务结果时，先等「口径接受」 |
| 「做下一项」 | 通过 CP-09 → 归档当前 task-state 并追加索引 → 新需求从 CP-01 开始（`previousTask` 指向归档） |

**一条指令串多步（谨慎）：** 用户说「确认需求并开始实现，做完跑 harness」= 跳过 CP-01 口头确认、**仍须在 CP-05 停**；**不能**跳过 CP-05 自动 commit。
