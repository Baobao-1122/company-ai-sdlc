# AI-Native 研发流程：多 Agent 架构设计

> **文档 ID：** `AGENT-ARCH-v0`
> **状态：** 设计草稿。未过 CP-01，不改 Rule、Skill、脚本
> **受众：** 标准库维护人、各业务项目负责人、Cursor Agent
> **关系：** 本文定义新流程的形态；[ai-native-optimization.md](ai-native-optimization.md) 中的同步、资产库、分档、规格目录等机制，作为本文的配套能力

---

## 1. 目标

company-ai-sdlc 是一套 **AI-Native 的企业级研发流程**。由 AI 主导**需求拆解、交互设计、视觉设计、架构设计、研发、测试、发布**各环节，从零搭建并持续迭代企业级项目与系统；人在关键检查点审核和拍板。

每个环节都满足三点：

1. **产出写进仓库**：可审、可续做、可对照代码。
2. **质量有机器兜底**：能写成检查的，不只写成文字。
3. **随项目变强**：每个环节由一个独立的 Agent 负责，有自己的方法、资产、检查和评测；每做完一个项目，经人审核后更新。

---

## 2. 设计原则

| # | 原则 | 含义 |
|---|---|---|
| 1 | **能力独立，运行按需** | 每个环节有独立的**能力包**，这是持续变强的来源。运行时是另开子 Agent 还是留在主对话，按环节特点定（§3） |
| 2 | **交接只认文件** | Agent 之间不靠聊天传话，只靠 `.sdlc/specs/<任务>/` 下格式固定的文件交接（§6） |
| 3 | **编排只调度，不干活** | 编排 Agent 判断路线、唤起 Agent、检查交接文件、在检查点停下；不写需求、不画交互、不写代码 |
| 4 | **按风险走路线** | 不同需求走不同的 Agent 组合；高风险由脚本强制升档（§5） |
| 5 | **人在检查点拍板** | 需求、设计、合并、发布、高风险操作由人确认；授权尽量落在 PR 审批上 |
| 6 | **能机器检查的交给机器** | 约束力从弱到强：文字、检查脚本、Cursor 钩子、CI。新规则须说明为何不能做成检查 |
| 7 | **测和写分开** | 写代码的 Agent 不负责判定自己是否合格；测试和审查由独立 Agent 做 |

## 3. Agent 划分

| Agent | 运行形式 | 读入 | 产出 | 人工检查点 |
|---|---|---|---|---|
| **编排** | 主对话 | 用户需求、task-state、各交接文件 | `route.md`、task-state | 路线确认（标准档、重型档开工时；快速档并入 CP-05）；汇总各检查点 |
| **需求** | 主对话，加载需求能力包 | 用户需求、产品模版、PRD | `requirements.md` | 需求确认（CP-01） |
| **交互设计** | 主对话出方案；子 Agent 检查 | `requirements.md`、交互资产 | `interaction.md` | 与视觉合并为设计确认 |
| **视觉设计** | 子 Agent | `interaction.md`、设计规范 | `visual.md`（含组件与样式约定） | 与交互合并为设计确认 |
| **架构** | 主对话出方案；子 Agent 审查 | `requirements.md`、`interaction.md`（A 类，路线经过时）、技术栈资产 | `architecture.md`、`tasks.md` | 架构审查（CP-02 前，条件触发）；设计与任务确认（CP-02） |
| **研发** | 主对话；大任务可拆给多个子 Agent 并行 | `tasks.md`（快速档为 `route.md` 的“快速档说明”）、技术栈资产 | 代码、migration、文档同步 | 外部依赖（CP-03）、范围外问题（CP-04） |
| **测试** | 子 Agent，与研发分开 | `requirements.md`（快速档为“快速档说明”）、`interaction.md`、`visual.md`（A 类，路线经过时）、代码 | `test-plan.md`、测试代码、验证结果 | 验证结果（CP-05） |
| **审查与发布** | 子 Agent（Bugbot、安全审查）加主对话汇总 | diff、规格文件 | `review.md`、PR | 提交（CP-06）、合并（CP-08）、发布（CP-10） |

**为什么这样分：**

- 要和人反复对话的环节（编排、需求、交互方案）留在主对话。Cursor 子 Agent 只能把结果交回主 Agent，中途不能问人。
- 输入明确、需要客观判断的环节（视觉、测试、审查）用子 Agent：上下文干净，不受前面对话影响。
- 研发的“写、跑、改”循环紧密，不拆开；只在任务彼此独立时并行。

**起步可合并：** 交互与视觉先合成“产品设计 Agent”，资产够了再拆。

## 4. 能力包：每个 Agent 变强的载体

能力包回答“这个环节**怎么做**”；资产库（§8）回答“**做过什么**可以复用”。

### 4.1 统一结构

```
agents/<agent>/
├── AGENT.md        # 角色、职责边界（做什么、不做什么）、工作步骤
├── contract.md     # 输入文件、输出文件、输出格式、完成标准
├── templates/      # 本环节的产出模板
├── lessons.md      # 经验记录：每条有来源（项目/PR）、日期、状态
├── evals.md        # 评测任务：改本能力包前必须回放；任务多了再拆成 evals/ 目录
└── checks/         # 产出合格的机器检查脚本；脚本建成前，检查项列在 AGENT.md 的“检查”表
```

### 4.2 与 Cursor 的对应

| 运行形式 | Cursor 载体 | 内容 |
|---|---|---|
| 子 Agent | `.cursor/agents/<agent>.md` | 薄入口：一句职责、`readonly` 等设置，正文要求先 Read `agents/<agent>/` 下的文件 |
| 主对话 | `.cursor/skills/<agent>/SKILL.md` | 薄入口：何时触发，正文指向 `agents/<agent>/` |

能力包本身是唯一真源，入口文件只做指向。Cursor 文档未说明子 Agent 能否自动加载 Skill，所以子 Agent 统一靠入口正文要求它直接 Read 能力包。

入口示例见 `templates/cursor-agents/`。标准库自身不放 `.cursor/agents/`，避免入口在本仓库的对话中生效；安装到业务项目时才放入该目录。

## 5. 编排：路线判定

### 5.1 三档

先按项目类型（§5.5）去掉不适用的 Agent，再按档位取默认路线。

| 档位 | 适用 | 默认路线 |
|---|---|---|
| 快速 | 文案、样式、文档、无业务语义的小修 | 研发 → 测试 → 审查；交接信息写在 `route.md` 的“快速档说明”（§6） |
| 标准 | 普通功能、页面 | 需求 → 交互（A 类改到界面时）→ 架构（产出 `architecture.md`、`tasks.md`）→ 研发 → 测试 → 审查 |
| 重型 | 新系统、新模块；权限、金额、数据库结构、对外接口、外部协议、生产发布 | 需求 → 交互、视觉（A 类）→ 架构 → 研发 → 测试 → 审查与发布 |

### 5.2 判定方式

1. **硬规则（脚本）**：按需求类型和预计改动路径判定，命中即强制升档。如改到 `lib/auth/**`、`app/api/**`、数据库 schema、金额口径，或新建系统、新建页面。规则写在项目配置中，由脚本执行。
2. **软判断（编排 Agent）**：硬规则未覆盖时，按需求内容判断，写出理由。
3. **路线确认**：编排 Agent 输出 `route.md`（档位、经过的 Agent、跳过的 Agent 及理由）。标准档与重型档在开工时请人确认一次，人可增减环节；快速档不单独停，档位与路线在 CP-05 汇报中一并说明，人认为判档有误时可退回重判（§7）。

### 5.3 回退

下游发现上游产出有问题时，由编排 Agent 退回对应 Agent 修改，下游不直接改上游文件。每次回退记一条，供编排和上游 Agent 复盘。

### 5.4 编排自己的提升

“判成快速档，后来发现动了权限”这类误判记入 `agents/orchestrator/lessons.md`，人审核后补进硬规则或判断依据。

### 5.5 项目类型

路线先看项目类型，再看档位。项目在 `AGENTS.md` 的项目扩展区声明类型；安装与升级命令（§11.1 第 7 步）落地后改为写入锁定文件。旧流程中的 Profile B 即这里的 B 类（来源：项目乙、丙的声明；项目代号见 [asset-library.md](asset-library.md) §6）：

| 类型 | 例子 | 交互、视觉 Agent | E2E 与截图验收 |
|---|---|---|---|
| A：有界面的 Web 平台 | 项目甲、丁 | 按档位启用 | 改到界面时必做 |
| B：数据或引擎服务，无界面 | 项目乙、丙 | 不启用；对外契约由架构 Agent 负责 | 不做；改用协议或接口级的黄金路径测试 |

### 5.6 开工检查

编排 Agent 在判档之前先做三件事（来源：项目丁 4 个任务验证后未提交、项目丙跳过 CP-06 后靠交接续做）：

1. 读 task-state 与 history 索引，列出**未收尾的任务**（验证通过但未提交、暂停中、CP-06 未过），请人决定先收尾还是挂起。
2. 挂起时在 task-state 写明交接信息：未提交的文件、下一步、阻塞点。
3. 检查项目红线是否齐全、规则中引用的命令在项目中是否存在；缺失时先报告，不开工。

## 6. 交接文件

每个任务一个目录 `.sdlc/specs/<taskId>/`。每份文件只有一个负责的 Agent，下游只读。

| 文件 | 负责 Agent | 必含内容 | 机器检查（示例） |
|---|---|---|---|
| `route.md` | 编排 | 项目类型、档位、路线、跳过理由、人工确认记录；快速档另含“快速档说明”（改什么、改动文件、1～3 条验收标准、验证命令），替代 `requirements.md` 与 `tasks.md` | 档位不低于硬规则判定；快速档说明齐全 |
| `requirements.md` | 需求 | 背景、范围与不做、用户故事、验收标准（编号）、沿用的产品模版及差异 | 每条验收标准有编号且可验证 |
| `interaction.md` | 交互设计 | 页面清单、页面流程、每页状态（空、加载、错误、无权限）、关键交互 | 每条验收标准对应到页面或状态 |
| `visual.md` | 视觉设计 | 采用的设计规范、组件选择、样式差异、视觉验收点 | 只用规范内的组件和样式变量 |
| `architecture.md` | 架构 | 运行形态、模块划分、数据模型、接口契约、技术决定 | 涉及 schema 时含 migration 与回滚计划 |
| `tasks.md` | 架构 | 实现任务拆分，每项含改动文件、验证命令、对应验收标准 | 每条验收标准至少被一项任务覆盖 |
| `test-plan.md` | 测试 | 用例清单（对应验收标准编号）、E2E 黄金路径、对账计划、截图验收（A 类项目改到界面时必填）、结果 | 每条验收标准至少一条用例；改到界面而无截图验收时不通过 |
| `review.md` | 审查与发布 | 审查结论、问题清单、复用候选 | 有结论；有复用候选判断 |

`.sdlc/task-state.yaml` 继续记录进度与断点，并新增指向当前 specs 目录的字段。

## 7. 检查点

本节是对现行 [human-checkpoints.md](human-checkpoints.md) 的**扩展与修改**：CP-01～CP-10 的编号和触发条件保留，按档位启用；新增“路线确认”“设计确认”两个检查点；快速档 CP-06 的人工确认方式有变更（见表下说明）。落地时须同步修改 `human-checkpoints.md` 与 `decision-rubrics.md`。

| 检查点 | 快速 | 标准 | 重型 |
|---|---|---|---|
| 路线确认（新增） | 并入 CP-05 汇报 | ✅ | ✅ |
| CP-01 需求确认 | — | ✅ | ✅ |
| 设计确认（交互/视觉，新增） | — | A 类改到界面时 ✅ | A 类 ✅；B 类不适用 |
| 架构审查（触发条件同现行 `sdlc-architecture`，不看档位） | — | 条件触发 | 条件触发 |
| CP-02 设计与任务确认 | — | ✅ | ✅ |
| CP-03 / CP-04 | 触发时 | 触发时 | 触发时 |
| CP-05 验证结果 | ✅ | ✅ | ✅ |
| CP-06 提交前审查 | ✅ | ✅ | ✅ |
| CP-07 / CP-08 推送与合并 | ✅ | ✅ | ✅ |
| CP-09 下一项 | ✅ | ✅ | ✅ |
| CP-10 高风险操作 | 触发时 | 触发时 | 触发时 |

**快速档 CP-06 的变更**（本文 §11.2 第 2 条）：只把人工确认由两步合为一步，审查结论与 commit 计划一并汇报，回复「确认提交」；「先修 review」「忽略：…」「暂停」「调整 message：…」等选项照旧可用。机器侧不减：`guard:sdlc-commit-rules`、`🔄 Reflection` 告知、Bugbot、命中敏感路径时的安全审查全部照跑；审查结论为“建议先修”时仍须先修。标准档与重型档的 CP-06 保持两步。

## 8. 资产库与提升闭环

### 8.1 资产库

沿用 [ai-native-optimization.md](ai-native-optimization.md) §2 的四层：流程层、技术栈层、能力模块层、领域层。准入判据、目录结构、状态版本、首批候选见 [asset-library.md](asset-library.md)。能力模块按 Agent 分片存放，例如“登录权限”模块：

| 分片 | 使用的 Agent |
|---|---|
| 产品规范与配置点 | 需求 |
| 页面流程与状态 | 交互设计 |
| 组件与样式约定 | 视觉设计 |
| 数据模型与接口契约 | 架构 |
| 模板代码 | 研发 |
| 契约测试 | 测试 |
| 已知坑 | 全部 |

### 8.2 提升闭环

```
项目任务完成
  → 各 Agent 复盘：可复用的模式、踩坑、误判
  → 写入候选清单（.sdlc/upstream-candidates.md）
  → 人审核：归入哪个 Agent 的能力包或资产库，能否做成检查
  → 回放该 Agent 的评测，确认没有变差
  → 合入标准库，能力包版本加一
  → 各项目按版本升级
```

**触发点固定**：每次提交前审查、每次线上问题修复、每次 PR 被打回。**合入必须人审**，不允许 Agent 直接写入标准库。

### 8.3 度量

每个 Agent 单独记录：产出被打回次数、下游回退次数、检查首次通过率。用于判断哪个 Agent 在变强、哪个需要投入。

## 9. 红线与机器拦截

- **一直生效的 Rule 只留红线**：数据红线（无 CP-10 授权禁止对生产库做任何写操作；校验、对账一律只读，含非生产的业务表；非生产验收库仅按 migration 链与测试需要读写，以 `data-redlines.mdc` 为准）、安全基线、CI 安全、提交规范（每次 commit 前必须 Code Review）。项目可追加项目级红线（如 mock 数据写库隔离），写在项目扩展中。其余规则进入各 Agent 能力包，按需加载。
- **Cursor 钩子**：用 `beforeShellExecution` 拦截危险命令，如在受保护分支 commit、命令中带生产库连接、对生产库执行写语句。钩子设 `failClosed: true`，钩子出错时也拦截。
- **子 Agent 只读**：审查类子 Agent 设 `readonly: true`；架构审查沿用“前后比对 `git status`，越权改动还原并作废”的做法。
- **CI 为最终依据**：PR 上跑 harness 与审查；Agent 本机结论只作参考。

### 11.3 分支与合并

| 分支 | 用途 |
|---|---|
| `main` | 旧流程，过渡期只修 bug；业务项目照常从这里同步 |
| `feat/ai-native-sdlc` | 重构集成分支，从 `main` 拉出 |

规则：

1. **`main` 的修复及时合入集成分支**：`main` 每合入一次修复，就把 `main` 合进 `feat/ai-native-sdlc`，避免最后集中解冲突。

3. **合并条件**：§11.1 第 1～3 步完成；试点项目已在集成分支上跑通快速、标准、重型各至少一个任务；迁移脚本可用。

## 12. 业务项目迁移

现有项目都在用旧流程。迁移成本是一次性的，与仓库方案无关；目标是每个项目只迁一次、每次迁移尽量小。

### 12.1 项目侧改动范围

新流程改的是 Agent 的协作方式，不改业务实现。

| 项目内容 | 处理 |
|---|---|
| 业务代码、数据库、接口 | 不动 |
| `test:harness:ci`、guard 脚本、CI 工作流 | 基本不动，命令名保持不变 |
| `.cursor/rules/`、`.cursor/skills/` | 受管文件整体替换为新版 |
| `.cursor/agents/` | 新增安装 |
| `AGENTS.md` | 换为精简版；项目专属内容移入项目扩展区 |
| `.sdlc/task-state.yaml` | 兼容旧格式，新增 specs 目录字段；`.sdlc/history/` 保留 |
| `.sdlc/specs/` | 新增，迁移后的新任务开始使用 |

### 12.2 主要难点：拆出项目定制

旧接入方式下，项目定制直接写进标准文件（见 [ai-native-optimization.md](ai-native-optimization.md) §1.1 P4），例如项目甲 `sdlc-workflow.mdc` 与标准库差 55 行、`sdlc-pr-review` 差 181 行。迁移时把这些差异拆为三类：

| 类别 | 去向 |
|---|---|
| 项目专属（如本项目的口径、路径、命令） | 项目扩展区（`AGENTS.md` 的项目扩展章节或单独的项目扩展文件） |
| 值得复用（如已试点的检查、规范） | 回灌候选，写入 `.sdlc/upstream-candidates.md`，经人审核后进标准库 |
| 已过时或新流程已覆盖 | 丢弃，在迁移记录中注明理由 |

迁移完成后，标准文件在项目中只读，以后升级整份替换，不再手工合并。

### 12.3 迁移脚本

一条命令完成迁移准备，人只审结果：

1. 检查前置条件：工作区干净；当前没有进行中的任务（task-state 已到 CP-09 或不存在）；本机标准库与远端一致；项目已声明类型（§5.5）。
2. 备份将被替换的文件到 `.sdlc/migration/<日期>/backup/`。
3. 对比项目文件与旧标准库对应版本，提取差异，生成 `.sdlc/migration/<日期>/extensions-review.md`：每段差异附建议类别（§12.2）。
4. 安装新版受管文件与 `.cursor/agents/`，写入锁定文件。
5. 检查红线是否齐全、受管规则中引用的命令（如 `guard:sdlc-commit-rules`）在项目中是否存在；缺失项写入清单（来源：项目丙规则引用了不存在的 guard，项目甲缺 3 条红线 Rule）。
6. 输出待人工确认的清单，不自动提交。

### 12.4 兼容原则

研发人员的使用习惯尽量不变：

- 检查点编号（CP-01～CP-10）、决策包格式、回复用语（「确认」「开始实现」「提交」等）不变。唯一例外是快速档 CP-06 合为一步确认（§7）。
- harness、guard、CI 的命令名不变。
- 旧 task-state 与 history 可直接读取。
- 新增的只有：开工时确认一次路线；交接内容写成 `.sdlc/specs/` 下的文件。

### 12.5 迁移节奏

1. **试点一个项目**，跑通快速、标准、重型各至少一个任务后，再迁下一个。
2. **未迁移的项目继续用旧流程**：集成分支合入 `main` 前从 `main` 同步，合入后从 `sdlc-legacy-final` tag 同步（§11.3）；过渡期旧流程只修 bug。
3. **在任务间隙迁移**：当前任务完成（CP-09）后再迁，不在任务中途切换。
4. **迁移本身作为一个任务**：走标准档。人工确认扩展清单后，跑 `test:harness:ci` 确认无回归，再按 CP-06 提交。
5. **全部项目迁完**后，停止维护 `sdlc-legacy-final`。

### 12.6 试点项目：项目丁

以地图大屏为主的 A 类项目，Vite + React 前端、Node 服务端（不是 Next.js）。盘点明细属于项目信息，不入标准库。

**适合试点的理由：** Skill 与标准库无分叉，迁移主要是 Rule 差异，可控；界面多，能验证交互与视觉两个新环节；历史任务多，可从中挑选评测任务。

**迁移前须处理：**

1. 当前进行中的任务先走完到 CP-09，再迁移（§12.5 第 3 条）。
2. 缺失的 `data-redlines`、`security-baseline` 在迁移时补装。`nextjs-middleware-response` 不适用于该技术栈，不安装；技术栈层 Rule 按项目技术栈选装。
3. 项目里的地图类 Rule：具体坐标、像素等数值留在项目扩展；通用做法按 [asset-library.md](asset-library.md) §2 判定，作为“地图轨迹回放”“高德地图”资产候选。
4. 无 CI 工作流：试点期间按 `templates/ci/` 补一份，作为“CI 为最终依据”（§9）的首个落点。
