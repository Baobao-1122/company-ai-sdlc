# 阶段 4：验证门禁

**对应 Skill：** `sdlc-verify`

## 目标

在汇报「完成」前，用命令证明变更可验收。

## 统一执行顺序（硬性）

条件门禁按下列顺序执行；**任一步失败则停止后续步骤（含 harness）**，进入 CP-05 推荐 **Stop**：

```text
（若改 schema）migration prepare → 应用 → 结构检查 → 依赖 API 冒烟
    ↓
（若命中业务数据影响面）只读抽样对账 → 输出结论与问题清单
    ↓
test:harness:ci
    ↓
CP-05 汇报
```

**禁止**在只读对账未完成（或失败）时先跑 `test:harness:ci`。Harness 绿不能替代业务结果核对。

## Agent 必须执行

```bash
# 仅在前置条件门禁全部通过后执行（按项目 package.json 为准）
pnpm test:harness:ci
# 或
npm run test:harness:ci
```

若项目有额外校验（如 `verify:dashboard`、只读 `reconcile:*`），按 `AGENTS.md` 的 Agent 执行规程追加；只读对账命令插入在 harness **之前**。

### 数据库结构变更（条件必跑）

本次修改表、字段、索引、约束或数据库枚举时，必须按顺序完成（**本段不含 harness**）：

1. 完成 migration prepare：工具生成，或手写后检查 journal/manifest，并确认已纳入版本管理
2. 将 migration 应用至本次验收使用的本地、测试或隔离集成库
3. 执行项目提供的迁移状态或数据库结构一致性检查
4. 针对性冒烟验证至少一个依赖新结构的 API 或数据访问路径；通用 Harness smoke 只有明确覆盖本次新增/变更结构时才能替代

环境暂不可用时，必须在 CP-05 标为 **Stop** 或明确的未完成项；migration 文件已准备不等于迁移已完成。

### 业务数据影响（条件必跑 · 只读）

CP-02 已声明命中数据影响面时，必须在 **`test:harness:ci` 之前**按计划完成**只读**抽样对账（可用项目脚本、SQL 或手工导出对比）：

1. 按计划取样本与指标
2. 对比基线（改前结果或外部真相）与改后结果
3. 输出**结论**（通过 / 有差异）与**问题清单**（差异项、可能原因、是否阻塞提交）
4. **禁止**在对账过程中对业务库做任何 INSERT / UPDATE / DELETE / TRUNCATE
5. 发现需修数时：只报告问题；修复必须另开任务并单独授权（写生产走 CP-10）

缺数字证据、核对未执行、或核对中改删了数据 → **不得进入 harness**，CP-05 推荐 **Stop**。  
结论为「有差异」但已给出问题清单时：**可以**继续跑 harness，是否允许提交由 CP-05 决策包判定。

结构验证（migration）与业务结果验证（本门禁）**互不替代**；两者都命中时：先结构链，再只读对账，最后 harness。

## 汇报模板

```markdown
## 验证结果

| 命令 | 结果 | 说明 |
|------|------|------|
| migration 应用与结构检查（涉及 DB 时） | ✅ 通过 | 目标环境：… |
| 依赖新结构的 API 冒烟（涉及 DB 时） | ✅ 通过 | … |
| 业务数据只读抽样对账（涉及数据影响时） | ✅ / ❌ | 只读：是；结论摘要：…；须在 harness 前完成 |
| test:harness:ci | ✅ 通过 / ⛔ 前置失败未执行 | … |
| verify:xxx | ⏭ 跳过 | dev 未启动 |

### 业务数据对账结论（涉及时必填）
- 样本与指标：…
- 基线 vs 改后：…
- 结论：通过 / 有差异
- 问题清单：（无则写「无」；有则逐条）
- 是否改删数据：否（必须为否）

### 如何手动验收
1. …
2. …
```

## 禁止

- 未跑命令就声称「已修好」
- 失败时不说明原因与下一步
- 涉及数据库结构时，只准备 migration 文件就进入 API 或页面验收
- 以校验/对账名义修改或删除业务数据
- 命中数据影响面却无结论与问题清单
- 只读对账未完成或失败仍执行 `test:harness:ci`
