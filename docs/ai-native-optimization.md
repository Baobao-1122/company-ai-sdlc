# AI-Native 研发流程优化方案

> **文档 ID：** `AI-NATIVE-OPT-v1`  
> **状态：** 方案，未实施。各期按 SDLC 单独立项，过 CP 后再改 Rule、Skill、脚本  
> **受众：** 标准库维护人、各业务项目负责人、Cursor Agent  
> **目标：** 让 AI 研发流程跨项目持续积累。项目 A 做完的能力、交互和踩坑经验，项目 B 一样时直接沿用，不重新调教一遍  
> **流程形态：** 编排 Agent 加各环节独立 Agent，见 [agent-architecture.md](agent-architecture.md)；本文的同步、资产库、分档机制作为其配套

---

## 0. 一句话结论

把对 Agent 的约束，从“写很长的文档让它记住”，改成**精简的上下文 + 机器强制的门禁 + 可复用的资产 + 自动的学习闭环**。

同步、回灌、升级都由机制兜底，不依赖人记得去做。

## 2. 目标形态：资产库四层

| 层 | 放什么 | 现状 |
|---|---|---|
| 流程层 | SDLC Rule、Skill、检查点、审查规范 | 已有，即本标准库现有内容 |
| 技术栈层 | Node + PostgreSQL + Drizzle 通用 guard、harness 模板、部署 SOP | 基本没有，散在项目甲 |
| 能力模块层 | 登录权限、列表表格、筛选汇总、导出、月报发布、外部数据对账等 | 只有 `login.md` 的产品口径 |
| 领域层 | 充换电、物流、车队通用规则，如北京时间自然日、金额口径、车队数据范围 | 散在项目甲与 `~/.cursor/skills`，未入仓库 |

**项目专属**内容（如外部标准的字段表、合作方的对账细节）留在各自项目，不进资产库。准入判据、目录结构、进库流程与首批候选见 [asset-library.md](asset-library.md)。

每个**能力模块**统一五件套：

1. 产品规范：沿用的能力与交互。
2. 配置点：哪些固定、哪些按项目填写，如角色数量、数据范围维度、会话时长。
3. 模板代码或内部包。
4. 契约测试：如越权拒绝、空绑定、多范围取交集。
5. 已知坑。

B 项目与 A 一致时直接安装；不一致时只改配置点。五件套在资产目录中按 Agent 拆为分片文件（`product.md`、`flow.md`、`ui.md`、`contract.md`、`code/`、`tests/`），见 [asset-library.md](asset-library.md) §3.1。

## 3. 优化方案

### 3.1 流程按风险分三档

> 档位路线与各档检查点**以 [agent-architecture.md](agent-architecture.md) §5、§7 为准**，下表为摘要。

开工时由 Agent 按改动路径和类型自动判定档位，边界不清时才问人。档位判定规则用脚本实现，例如改到 `lib/auth/**`、`app/api/**`、数据库 schema 自动升为重型。

| 档位 | 适用 | 主要人工介入点 |
|---|---|---|
| 快速 | 文案、样式、文档、无业务语义的小修 | 验证结果（路线确认并入此处）；提交前审查（人工确认合为一步）；合并 |
| 标准 | 普通功能、页面 | 路线；需求；设计（有界面时）；架构审查（条件触发）；设计与任务；验证结果；提交前审查；合并 |
| 重型 | 新系统、新模块；权限、金额、数据库 schema、对外接口、外部协议、生产发布 | 标准档全部，加对账结论、发布 |

三档都在**每次 commit 前跑 Code Review**（Bugbot 等机器审查不减）；CP-03、CP-04、CP-10 按触发条件启用。

纯查询、对账、答疑类任务不进开发 SDLC，只加载只读红线。

### 3.2 规格驱动：过程产物写进仓库

> 交接文件完整清单、负责 Agent 与机器检查**以 [agent-architecture.md](agent-architecture.md) §6 为准**，下表为摘要。

每个需求一个目录，如 `.sdlc/specs/FU-xxx/`：

| 文件 | 内容 |
|---|---|
| `route.md` | 档位、路线与人工确认记录 |
| `requirements.md` | 需求与验收标准 |
| `interaction.md`、`visual.md` | 交互与视觉设计；沿用了哪个能力模块、差异点 |
| `architecture.md` | 技术方案与接口契约 |
| `tasks.md` | 拆好的实现任务，每块带验证命令 |
| `test-plan.md`、`review.md` | 测试用例与结果；审查结论 |

人审这些文件的 diff，不审聊天里的决策包。换对话、换人、换模型都能续做；PR 审查可拿规格对照代码；回灌资产库时直接从规格提炼。

### 3.3 上下文工程：变薄、按需加载

- `AGENTS.md` 控制在 150 行左右：项目是什么、红线、关键路径、常用命令，加一张“细则在哪”的索引。
- 一直生效的 Rule 只留真正的红线，如数据红线（禁止擅自写生产库；对账一律只读，含非生产的业务表；以 `data-redlines.mdc` 为准）、提交规范（每次 commit 前 Code Review）；项目可追加项目级红线，如 mock 数据写库隔离。其余按文件路径自动挂载。
- 流程细则下沉到 Skill，到对应阶段再读。
- 每条规则只写在一处，其他地方只放链接；加 guard 检测重复的规则文字。

### 3.4 能机器检查的，一律交给机器

约束力从弱到强：文字规则、guard 脚本、Cursor 钩子、CI。能往后放就往后放。

- **Cursor 钩子**：Agent 执行命令前拦截危险操作，如在受保护分支 `git commit`、命令中带生产库连接、对生产库执行写语句。
- **CI 作为最终依据**：PR 上自动跑 `test:harness:ci` 与 Bugbot 审查；Agent 本机结论只作参考。
- **人工审批挂在 PR 上**：合并、发布的授权用 PR 审批与分支保护实现，不靠聊天里的“确认”。
- **新规则准入**：新增规则须说明为何不能做成检查；能做成检查却只写文字的，不收。

### 3.5 同步机制：不靠人记

| 方向 | 机制 |
|---|---|
| 标准库到项目（升级） | 项目放锁定文件 `.sdlc/standard.lock.json`，记录标准库版本、每个受管文件指纹，以及已安装的资产与版本（见 [asset-library.md](asset-library.md) §4）；一条命令负责安装与升级，执行前确认本机标准库与远端一致，否则拒绝；漂移检查 guard 接入 `test:harness:ci`，受管文件被私改即报错，版本落后给警告；定时任务每周检查，落后自动提升级 PR |
| 项目到标准库（回灌） | CP-06 增加“复用候选”判断，结论写入 `.sdlc/upstream-candidates.md`；新增 guard、Rule、Skill 却无复用判断时拦截；每月定时任务汇总各项目候选，向标准库提回灌 PR，由人审核 |
| 项目之间 | 禁止直接复制：受管文件头部带来源版本标记，带标记但不在锁定文件中的文件由 guard 报错，提示改为从标准库安装 |
| 全局 Skill | 纳入资产库仓库，用同一条命令安装到本机，同样记录版本 |

标准文件在项目中只读；项目扩展只写在 `AGENTS.md` 的“CP 判断扩展”或单独的项目扩展文件中，升级时整份替换受管文件。

三档兜底：

1. **拦截**：harness 中的 guard、提交钩子，不处理无法合并。
2. **主动提醒**：定时任务定期检查、自动提 PR。
3. **会话提醒**：Agent 开工先读锁定文件，版本落后先告知。

### 3.6 学习闭环：每次都学，定期汇总

- **固定触发点**：每次提交前审查、每次修复线上问题、每次 PR 被打回，判断“能否复用、属于哪一层、能否做成检查”，写入候选清单。
- **优先做成检查**：踩坑经验先变 guard 或测试，做不成再写规则。
- **规则有出处和寿命**：每条规则记录来源（事故或 PR）、负责人、最后验证日期；长期未触发且无项目使用的定期清理。

### 3.7 给 SDLC 本身做评测与度量

- **流程评测集**：十几个典型任务场景定期回放，检查 Agent 行为。例如：只读对账任务有没有尝试写库；改权限是否自动升为重型；小改动有没有被要求走全套检查点。改 Rule 或 Skill 前先跑。
- **效果指标**：每个功能被打回次数、harness 首次通过率、上线后缺陷数、需求确认到合并的时长。各项目都记，用于对比复用是否生效。

### 3.8 并行与后台执行（第三期）

互不依赖的任务放到独立 git worktree 或云端 Agent 并行；PR 创建后自动触发审查；定时巡检同步状态、依赖安全、文档是否过期。

## 4. 不建议照搬的做法

| 做法 | 原因与替代 |
|---|---|
| 强制规则靠 MCP 在运行时检索 | Agent 可能不查、查错版本，结果不稳定；改为按版本安装 |
| 自动合并、自动发布 | 金额、权限、生产相关仍由人审批 |
| 交付后由 Agent 全自动提炼并直接写入资产库 | 提炼可自动，合并必须人审 |
| 一开始把所有项目的规则合进资产库 | 先分层，否则只是把噪音集中到一处 |

## 5. 落地路线

| 阶段 | 内容 | 完成标准 | 对应问题 |
|---|---|---|---|
| 第一期 | 统一版本号、锁定文件、安装升级命令、漂移检查 guard；项目甲与项目乙接入；项目甲已试点的检查回灌标准库；更新过时说明 | 两个项目一条命令可升级；漂移被 harness 拦截；不再有项目间直接复制 | P1–P6、P10 |
| 第二期 | 风险三档、规格目录、`AGENTS.md` 瘦身与规则去重、Cursor 钩子拦截红线、PR 上的 CI | 每次对话固定加载的上下文减半；红线由钩子拦截 | P11–P15 |
| 第三期 | 能力模块（先做登录权限，含数据范围）、全局 Skill 入库、复用候选与月度回灌、流程评测集与效果指标、定时任务 | 新项目装配登录权限模块后只填差异点 | P7–P9 |

第一期优先：后续所有自动化都依赖版本号和锁定文件来判断“谁落后、谁被私改”。

第一期开工前，先做一次只读差异盘点：把项目甲、项目乙与标准库的差异逐个分为“该回灌”“该留在项目扩展”“该直接升级”三类，作为第一期的输入。
