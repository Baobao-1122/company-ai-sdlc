# SDLC · 架构审查

只审技术方案和运行架构。不写代码，不改文件，不替代 CP-06 的 Bugbot。

## 何时必须调用

命中**任一**条，就在给出「开始实现」之前调用本 Skill：

| # | 触发 |
|---|------|
| 1 | 新项目或新服务的**首版运行形态**：进程怎么分、用什么数据库、原件或文件放哪、任务怎么跑 |
| 2 | **改变**已接受的运行形态：队列、并发、部署拓扑（例如同一台数据库改成独立实例）、新增一类持久化 |
| 3 | **第一版**跨系统数据归属或对外契约：谁保存权威数据，快照、数据集或分发怎么交出去 |
| 4 | 引入新的执行模型：消息队列、独立 Worker、流式处理、把大批次和小任务分成不同处理通道 |
| 5 | 用户明确说「评审技术方案」「架构审查」或 architecture review |

新项目不是每个需求都审。只审上面这种会定下后续实现都要跟着走的方案。第一个运行架构要审；后面的小功能不审。

## 何时不调用

下面几条**同时成立**时不调用，把 `status` 写成 `not_required`，并在设计里写一句理由：

- 缺陷修复、文案、样式，或在已接受契约里增补字段
- 按已接受的 ADR 或架构实现，不改进程、存储位置、任务模型和系统边界
- 依赖只是补丁升级，不改变数据流
- 本次没有命中上表任一触发

判断冲突时，以上表「必须调用」为准。

### 例子

| 场景 | 调用 |
|------|------|
| 新系统第一次定数据库、任务处理和部署 | 调用 |
| 生产库从共用实例改为独立实例 | 调用 |
| 已定流水线后新增一个来源适配器，任务模型和存储不变 | 不调用 |
| 改按钮、修一个已有接口字段 | 不调用 |

## 调用方式

主 Agent 先写好要审的方案（对话中的方案或已落盘的设计均可），再启动**一个**子 Agent：

- `subagent_type`: `generalPurpose`
- `description`: `Architecture Review`
- `run_in_background`: false
- 提示词使用下方模板

平台没有单独的只读子 Agent 类型。`generalPurpose` 仍可能改文件。约束分两步：提示词禁止它改文件；主 Agent 在它返回后核对接住越权改动。

调用前记下仓库的 `git status --short`。子 Agent 返回后再看一次。审查期间多出来的修改或未跟踪文件，一律还原：已跟踪文件用 `git restore`，审查新建的未跟踪文件删除。然后宣布本轮审查作废，重开一轮。不得留下这些改动，也不得采纳该轮结论。

调用前在聊天标明：

```markdown
🔄 **架构审查** · 另开只读 Agent 审技术方案

| 项 | 说明 |
|----|------|
| **触发** | （命中的那一条） |
| **你需要做什么** | **无需回复**；完成后给你审查结论 |
```

未命中触发时**禁止**启动该 Agent。

## 审查标准

审查 Agent **只使用本节**，不得在当轮另起标准。先读方案点名的已接受 ADR、契约和项目边界。已接受的决策是依据；本节检查方案有没有把这些决策落成可运行的形态，以及有没有新的运行风险。

不得用行业文章、另一套产品或个人偏好推翻已接受的 ADR。方案与已接受文档冲突时，记在 A1：改方案，或先修订 ADR。不得静默改口径。

| 编号 | 审什么 | 通过 | 要改 |
|------|--------|------|------|
| A1 | 与已接受决策一致 | 进程、存储、任务、系统边界都能指到已接受文档；新的收紧写明落实的是哪一条 | **高**：和已接受的句子冲突，或把未接受的讨论稿当成已定 |
| A2 | 失败与重放 | 失败能从原件或等价输入重跑；重跑不产生第二份已发布数据；幂等键在写入已发布数据之前就能计算 | **高**：写到一半会改已发布数据，或失败后无法重放 |
| A3 | 并发与阻塞 | 多个执行者不会同时做完同一件已发布工作；长任务有单独占用方式，加大并发不必换模型 | **中**：没有领取或租约；一种长任务会占住以后所有任务 |
| A4 | 资源上限 | 大输入有明确的时间、内存或分片边界，不把整份输入放进一次内存或一个事务 | **高**：方案依赖整份加载或无上限批次。没有大输入时写「不适用」 |
| A5 | 部署隔离 | 本地和生产分别写明数据库实例、库名、原件放哪 | 项目或数据红线已要求生产分开时为 **高**，否则为 **中**：只写了库名，没写是同一实例上的独立库还是独立实例 |
| A6 | 扩展缝 | 写明以后新增入口或出口时哪一段保持不变；新入口进入同一条核心链 | **中**：新入口必须重做存储或任务模型 |
| A7 | 依赖是否必要 | 新的中间件或重型库写明现有数据库或语言做不到的事 | **中**：用新中间件替代现有数据库已经能做的领取、重试或状态 |
| A8 | 这一刀的边界 | 写明这次实现证明什么，哪些能力明确后置 | **低**：后置能力和这一刀混在同一次必须完成的范围里 |

某条所依赖的组件这次没有，写「不适用」并给一句理由。不适用不算要改。

**总结论：**

- 有任一高 → **要改**
- 没有高、有中 → **要改**；人可以「维持方案」并写理由
- 只有低，或全部通过 / 不适用 → **通过**
- 方案只是复述已接受架构、没有新的运行选择 → **这次不该审**

问题表只收录要改的条：严重度、编号、方案位置、问题、建议。

### 提示词模板

```text
你是架构审查 Agent。不要修改文件，不要给出实现代码，不要执行会写入仓库的命令。发现自己要改文件时停下来，只输出审查结论。

先 Read 项目内 `.cursor/skills/sdlc-architecture/SKILL.md` 的「审查标准」。只按 A1–A8 审查，不得另起标准。

审查这份技术方案：
<方案全文>

已接受的依据（冲突时以这些文档为准）：
<ADR、契约、项目边界的路径>

输出：
1. 触发复核：该审 / 这次不该审
2. 总结论：通过 / 要改 / 这次不该审（按审查标准的总结论规则）
3. 标准表：A1–A8 各一行，值为通过、要改或不适用，并写一句证据
4. 问题表：只收录要改的条。没有则写「无」
```

## 审查之后

先按上一节核对工作区。审查作废时不进入下面的分支。

**总结论是「这次不该审」：** 不展示下面三项，也不在这一步给出「开始实现」。把子 Agent 的理由写成 `架构审查未触发：…`，`extensions.architectureReview.status` 记 `not_required`。然后输出 CP-02。是否开始实现只在 CP-02 询问。

**总结论是「通过」：** 把结论汇总给用户并暂停。`extensions.architectureReview.status` 先记 `pending_confirm`。此状态不得输出 CP-02，也不得给出「开始实现」。

```markdown
### 请你回复
1. **「确认通过」**
2. **「暂停」**
```

用户回复「确认通过」后，把 `pending_confirm` 改为 `reviewed`，再输出 CP-02。`pending_confirm` 期间不得输出 CP-02。

**总结论是「要改」：** 把结论汇总给用户并暂停。`extensions.architectureReview.status` 记 `changes_requested`。此状态不得输出 CP-02，也不得给出「开始实现」。

```markdown
### 请你回复
1. **「按审查改方案」**
2. **「维持方案：…」** — 写明不改的理由
3. **「暂停」**
```

- 「按审查改方案」后，立刻把 `status` 改为 `revising`，然后改方案并再审。`revising` 不得输出 CP-02，也不得再次询问「按审查改方案」。再审结论仍按本节处理：「通过」时改为 `pending_confirm` 并再次暂停，用户回复「确认通过」后才进入 CP-02；「要改」时改回 `changes_requested` 并再次暂停；「这次不该审」时改为 `not_required`，写未触发理由后进入 CP-02。不得因为已经再审过就跳过「确认通过」。
- 「维持方案」后进入 CP-02，把理由写入 `extensions.architectureReview`，`status` 记 `waived`。
- 主 Agent 自己判断未触发、没有启动子 Agent：把 `extensions.architectureReview.status` 写成 `not_required`，在 CP-02 设计里写 `架构审查未触发：<一句理由>`，然后进入 CP-02。

## 任务状态

有 `.sdlc/task-state.yaml` 时写入：

```yaml
extensions:
  architectureReview:
    required: false
    reason: ""
    status: not_required # not_required | pending_confirm | changes_requested | revising | reviewed | waived
```

`waived` 只用于用户选择「维持方案」。

## 禁止

- 小改动也启动本 Agent
- 用本 Agent 代替 Bugbot 或 Security Review
- 子 Agent 改代码或提交
- 命中触发却跳过审查直接「开始实现」
