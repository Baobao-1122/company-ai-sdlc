# SDLC · 合并前 PR Review（CP-08）

**先读：** `docs/pr-review.md`（业务项目为 `docs/qa/ai-sdlc-pr-review.md`）。

## 硬性规则

- 先完成本 Skill，再谈 Merge。Merge 默认由人完成。
- 写代码的 Agent 读过 diff，不能代替本 Skill 的 Bugbot。
- 结论必须完整出现在聊天里，并写入 PR 正文。禁止只留在 PR 里。
- `gh pr create` 与 `gh pr merge` 不得在同一轮执行。
- 「push 并合并」只授权 push、审查和开 PR。
- 项目未声明可验算业务结果时，写「无需人工判断业务结果」，不编造核对题。

## 触发

| 用户说 | 动作 |
|--------|------|
| 「提 PR」「开 PR」「合并 dev」「合进 dev」 | 进入本 Skill。未 push 则先按 CP-07 推送功能分支 |

## 步骤 0 · 能否开始

同时满足才继续：

1. 当前分支不是 `dev`、`main` 或生产镜像分支
2. 功能分支已 push
3. `git log origin/<集成分支>..HEAD` 至少一条提交
4. 项目验证命令在该分支上已通过；不确定就重跑
5. 已读项目 `AGENTS.md` 的 CP-08 扩展，确认这次 diff 是否命中可验算业务结果，以及项目声明了哪些合并前必查项

缺任一条：说明缺什么并停止，不创建 PR。

## 步骤 1 · 告知 Reflection

```text
🔄 Reflection · CP-08 · PR Review（相对 origin/<集成分支>）
- 本次对比：<分支> @ <sha>，<n> commits
- 可验算业务结果：未命中 / 命中（<类别>）
- 你需要做什么：无需回复。完成后按结论决定是否合并；若命中，先回答口径题
```

## 步骤 2 · 只读审查

1. 用 `git diff origin/<集成分支>...HEAD` 确认范围。
2. 启动 **Bugbot**，`Diff: branch changes`。Custom Instructions 使用项目审查关注点，并要求对照 `docs/pr-review.md`：部分覆盖必须明示。
3. 命中安全、权限、API、认证路径时，再启动 **Security Review**，同样使用 `branch changes`。
4. 若 Bugbot 声明只覆盖部分 diff，记录未覆盖的文件或提交。

## 步骤 2.1 · 合并证据

按 `docs/pr-review.md` §2.1 逐行收集：

1. 项目验证命令的结果。
2. 分支改了数据库结构：migration 链各步结果。
3. 分支命中业务数据影响面：只读对账结论和数字。
4. 列出改动里没有自动化测试在真实依赖上执行过的代码路径。只有测试替身、类型检查或人工审查覆盖的，都算未执行。
5. 项目声明的合并前必查项：逐项写结果和证据。项目没有声明就写「无」。

适用的证据缺失或必查项不通过，结论为 ❌。有未执行路径或必查项未执行，结论最高 ⚠️，并写进保留项。不得为了凑 ✅ 把未执行写成通过。

## 步骤 3 · 样本与判断题

命中可验算业务结果时，在写结论前备齐：

- 改变的规则和影响范围
- 一条会变的具体输入与结果
- 一条不变的具体输入与结果
- `docs/pr-review.md` §4 的六行人工判断

样本来自本次测试、只读查询或已记录的验证。凑不齐时总体结论写 ❌，不建议合并。

未命中时跳过本步，结论中写「无需人工判断业务结果」。

## 步骤 4 · 结论与 PR

1. 按 `docs/pr-review.md` §5 写出「PR 审查结论」。
2. 聊天先贴完整结论，再贴决策包。
3. 创建或更新 PR。正文含 `## Summary`、`## Test plan`、`## Agent PR Review`（粘贴结论全文）。
4. 发 `🔄 Reflection · CP-08 · PR Review · 完成`。

## 步骤 5 · CP-08 步骤 1

决策包必须含 ①～⑤，并停止。

- ① 目的：决定是否把该分支合并进集成分支
- ② 判断要点：使用 `docs/decision-rubrics.md` CP-08；命中时追加口径是否已接受
- ③ 自检：结论标记、Bugbot 覆盖、合并证据与未执行路径、两条样本或「无需人工判断业务结果」
- ④ 推荐：✅ 且口径已接受（或无需判断）→ 可以合并；⚠️ → 先看保留项；❌ → 先修
- ⑤ 请你回复：
  - 未命中：「去 GitHub Merge」/「先修 PR」/「暂停」
  - 命中：「口径接受」/「口径不接受：…」

`⏸ CP-08 · 步骤 1/2 · PR Review 暂停`

## 步骤 6 · Merge

仅当下一条消息明确授权，且结论为 ✅ 或用户已接受的 ⚠️。命中可验算结果时，还须已收到「口径接受」。

执行项目使用的 merge 命令（通常 `gh pr merge`）。合并后汇报 PR URL 与合并提交。不得在步骤 5 的同一轮执行。

## 与 CP-06 的区别

| | CP-06 | CP-08 |
|--|-------|-------|
| 时机 | 每次 commit 前 | 合并进集成分支前 |
| 范围 | 本次未提交 diff | `origin/<集成分支>...HEAD` |
| 业务样本 | 不要求 | 仅命中项目声明的可验算结果时要求 |
| 关系 | 两者都要做。PR 审查不替代 commit 审查 | |
